# 当前版本性能复查（2026-09-18）

审查对象是 `d97641b` 加当前工作区未提交的业务改动，包括新的可选择文本控件、Emoji 宽度测量及会话过滤。此次没有修改业务源码；测试与合成数据脚本放在已忽略的 `src/IlMatto.Desktop/artifacts/performance-audit-2026-09-18/`。没有启动 Provider、Chrome 或读取真实会话。当前 16 项桌面回归通过。

仍有可优化空间。优先处理流式通知与全量扫描，保持现有文字选择、图片绘制、真实行高、阅读位置补偿和拖动期间持续渲染。下面的数值来自本机合成测试，不等于实际使用时的整机 CPU、常驻内存或帧率。

## 1. 让流式更新真正合并，并缩小属性通知范围

位置：`ManagerViewModel.cs:1938` 的 `EnsureManagerTypewriterStarted`，以及 `1527` 的事件收尾路径。

`QueueManagerText` 每个增量都会调用 `EnsureManagerTypewriterStarted`，后者无条件同步执行 `RenderManagerTypewriterTick`。若每个增量较小，本次调用就会将待处理文本清空，33 ms 定时器无法起到合并作用。每个事件还会复制 Activities/审批状态，并通知 9 个名称、工作区、连接及上下文属性，即使它们没有变化。

实测：通过实际 ViewModel 的断开连接测试入口连续输入 2,000 个“测试”增量，在任何定时器 tick 之前就收到 2,000 次 Text 属性通知，用时约 52.6 ms。这是模型层通知数量，不是声称 WPF 实际绘制了 2,000 帧。

建议：首段立即显示；后续增量在约 33 ms 窗口内合并，使用一个有界、保序的事件队列。工具边界、完成、取消、会话切换和关闭之前排空队列。仅在对应值变化时通知名称/Provider 属性；活动列表变化时才同步列表。管道 JSON 解析也可以移出 UI 同步上下文，再批量投递。不要把同步调用简单替换成每条事件一个无限积压的 BeginInvoke。

这与拖动滚动条时的 Markdown 渲染队列无关，不需要恢复“松手后才渲染”的规则。验收应保留首段响应、工具顺序、最终文本、取消/退出恢复和阅读位置测试。

## 2. 记忆分页改为按需读取，避免每页解析整份原文

位置：`companion-memory.ts:231` 的 `readSessionPage` 和 `272` 的 `readTranscriptEntries`。

当前每次翻页都 `readFile` 整个 JSONL，`split` 全文并解析所有消息，最后才选取本页最多 16,000 字符。返回值有长度限制，但读取和解析成本仍随整份历史增长。`openSession` 也有全量读取及排序路径。

使用当前 ManagerHost 的对应构建、Node v24.15.0，预热一次，调用前执行 GC，测试结果：

| 合成原文 | 返回正文 | 一次分页耗时 | 调用后 JS 堆增长 |
|---|---:|---:|---:|
| 1,000 条、3.97 MiB | 16,000 字符 | 11.2 ms | 12.2 MiB |
| 10,000 条、39.73 MiB | 16,000 字符 | 85.5 ms | 121.7 MiB |

每条测试正文是 4,096 个 ASCII 字符。堆增长为调用前后 `heapUsed` 的差值，不是峰值、泄漏或常驻内存；读取时间受文件缓存和 GC 影响。

建议：JSONL 流式读取，并使用有界的行号/字节偏移索引定位下一页；保留已有游标中的消息序号、消息内偏移，以及截断消息续读语义。损坏尾行、文件追加/删除和旧游标兼容需要回归。避免用无上限全文缓存代替整文件读取。

## 3. 滚动热路径改为按变更同步，减少全历史遍历

位置：`ChatTimelineLayoutIndex.cs:145`、`:165`，`ChatTimelineController.cs:320`、`:431`。

每次滚动刷新调用 `Synchronize`，即使集合和宽度未变，也会用 `SequenceEqual` 检查整份消息列表。消息变更时 `IndexOf` 线性寻找行号；控制器还遍历所有曾创建过的行模型，重新筛选范围，并取消重建渲染队列。可见控件已经虚拟化，数据管理部分仍有随历史长度增加的工作。

实际布局索引的合成计时（每项 1,000 次调用）：

| 消息数量 | 未变化的 Synchronize | 最后一行 Invalidate |
|---|---:|---:|
| 100 | 2.10 ms | 0.51 ms |
| 1,000 | 19.79 ms | 3.82 ms |
| 10,000 | 196.91 ms | 30.43 ms |

这里的 196.91 ms 是 1,000 次合计，单次约 0.197 ms，并不是一次滚动卡住 197 ms。单独成本不算最大，但会与高频流式通知及布局事件叠加。

建议：CollectionChanged/宽度变化时才重建索引；维护消息对象到行号的映射；离屏释放仅检查上一个显示范围。渲染范围未变时保留队列，继续可见区域优先、每批两行。保留现有 Fenwick 高度计算及锚点逻辑，不通过降低渲染频率来掩盖多余遍历。

## 4. 保存时复用未变化会话的快照

位置：`ManagerConversationStore.cs:163` 和 `ManagerConversationWriter.cs:44`。

后台序列化和 500 ms 请求合并仍有效。但每次保存的 UI 快照捕获仍遍历至多 100 个会话的所有消息，并复制全部 DTO 集合；只有一个草稿变化也会做这些工作。

仅测快照捕获、不执行文件写入，20 次平均：1,000 条消息约 1.19 ms / 0.45 MiB 分配；10,000 条消息约 18.94 ms / 4.60 MiB 分配。正文为每条 1,024 个中文字符，字符串本身按现有实现共享。

建议先按会话维护脏版本，复用未变化的不可变快照，继续保留现有 JSON 格式和后台顺序写入。这样收益主要在 UI 捕获阶段，全量文件序列化成本仍存在。进一步拆分会话文件和按需加载属于更大的存储改造，应单独处理迁移、删除和失败恢复。

## 5. Browser MCP 快照可合并跨进程读取

位置：`browser-mcp.ts:217` 的 `snapshot`。

最多 100 个控件，每个控件依次读取 tag、role、aria-label，以及回退用的 innerText/placeholder。按当前路径，仅控件属性部分就有约 300～500 次串行 Playwright 调用，页面正文则先完整传回 Node 再裁剪。这是源码确认的调用数量，尚未启动真实 Chrome 测量耗时。

建议批量提取控件属性，并在页面端先限制正文长度，再一次返回结果。保留元素顺序、e1/e2 引用、标签优先级及可见文本语义；不需要改变用户配置的页面 JavaScript 权限。该项对日常聊天影响较小，优先级低于流式与长历史路径。

## 暂不列为高收益项

- 可选择的 TextBox/RichTextBox 是新增功能，不能为了性能退回不可选择文本。虽然默认撤销开关为 true，但当前离屏构造实验中两种设置的旧段落 WeakReference 均为 0/20 存活，未证实撤销历史滞留，因此未将其列为已确认的内存问题。
- Markdown 解析缓存已有条数和字符总量上限，图片也会在控件卸载时释放；没有必要继续增加无界缓存。
- TaskTraceStore 仍有全量解密/追加/重加密路径，但当前统一 Manager 的日常路径是否高频产生 task_trace 尚未得到运行证据，不把它列为当前主要瓶颈。

建议先实施 1 和 3 改善聊天交互，再做 2 改善长会话回忆的内存峰值；4 随真实历史规模安排，5 按浏览器工具的使用频率安排。
